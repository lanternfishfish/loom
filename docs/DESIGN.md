# Loom：设计与实施计划 v1.0

> 这是本仓库的设计文档，与代码同步维护。实现见仓库根目录的 `loom.py`（单文件，只用标准库）。
> 定位：**与领域无关的 agent 长时间自治框架**。CTF 是它的第一个 profile，不是它的定义。
> 写作原则：协议里每写一条，都先回答"不写会怎样"。答不上来的，删掉。

> **名字**：Loom，织机。经线是张紧不动的框架（`CLAUDE.md` / `OBJECTIVE.md` 冻结），纬线是一次次会话，梭子穿过一趟布上就多一行（`log.md` / `summary.md`）。线断了打个结继续织（`## 断点`）——不会有哪一次断线把整匹布废掉。一台织机同时只有一个人踩，这就是单一写者。断一次不废整匹布，正是"会话会死，文件不会"的另一种说法。

---

## 〇、一句话与三条基调

**一个共享目录 + 两个角色 + 一个时钟。**

三条基调，后面每一条设计都是它们的推论。有争议时拿它们当判据：

1. **文件即记忆** —— 会话可以死，文件不会；文件还能被退回去（§6）。
2. **单一写者** —— 不靠锁，靠"这个文件只有你能写"。
3. **信任与放权** —— 框架只管流程（谁在跑、跑多久、下一个是谁），不管质量（做得好不好）。**能用一句 prompt 说清的，不写进协议；能交给模型判断的，不写成流程。**

由此得到一条划分工作的方法：

> **要么它是一个"流程分支"（loom 必须知道才能决定下一步动作）→ 写进 loom.py。
> 要么它是一个"判断"（需要理解内容）→ 写进 prompt，交给模型。
> 没有第三种。** 介于两者的东西（半自动检查、启发式阈值）是这套系统最主要的腐化源。

## 一、角色：只有两个（判据比结论重要）

角色划分的判据**不是"有哪些职责"，而是"是否需要同时持有不同的上下文"**。

- planner 的上下文：全局摘要（有哪些任务、各自一句话结论、目标达成没有）
- worker 的上下文：单任务的细节与试错历史（试过什么、报了什么错、下一步具体命令）

这两份上下文互相排斥：任务细节塞进 planner 会淹没全局判断，全局讨论塞进 worker 会挤掉工作记忆。所以必须是两个进程。

反过来，侦察 / 攻坚 / 复核 / 写文档 / 修工具 —— **都不需要不同的上下文，只需要不同的任务描述**。它们是任务，不是角色。v0.2 的 4 角色按这个判据自然折叠成 2 个。

> 复用到新领域：**想加角色前，先问"它需要一份别人看不见的上下文吗"。不需要，就写成任务。**

| 角色 | 看什么 | 写什么 | 会话策略 |
|---|---|---|---|
| **planner** | `OBJECTIVE.md` + `STATE.md` + 各任务 `task.md`/`summary.md` | `STATE.md`、新建 `task.md` | **每次新建**，记忆只有 `STATE.md` |
| **worker** | 本任务 `task.md` + `log.md` 尾部 + 产物 | 本任务 `log.md`（追加）、`summary.md` | **每任务固定一个 session id**，全程复用它 |

## 二、对象：四个文件，各一个写者

```
work/                       # 一个 git 仓库，单线，不建分支
├── CLAUDE.md              # 宪法：角色、纪律、目录约定（每会话必读；人写）
├── OBJECTIVE.md           # 意图 + 验收标准（冻结，只有人能改）
├── STATE.md               # planner 独占写：任务表 + next_task + 决策日志（≤120 行）
├── tasks/task-NN-<slug>/
│   ├── task.md            # 契约：目标 / 完成判据 / 约束 / budget_min   ← planner 写一次，冻结
│   ├── log.md             # 过程：进展、报错、排除的路径、## 断点        ← worker 只追加
│   ├── summary.md         # 陈述：结论 / 做了什么 / 产出在哪 / 下一步     ← worker 写（≤30 行）
│   ├── solve/             # 可复现脚本，run.sh 一键重放                  ← worker 写
│   ├── artifacts/         # 解包/反编译/dump，gitignored，可整体删除
│   └── .state             # 机器事实：queued/running/timed_out/exited + sid + pid + pid_start
├── shared/                # 跨任务共享（脚本、参考、死路清单），新增不改他人的
├── sessions.log           # loop 写：时间 / sid / 角色 / 任务 / 事件，append-only
├── human.log              # loop 写：人做过的每一次介入（-p 文本 / 检测到的文件改动），append-only
└── .gitignore             # 分界线：可重建的不进 git（§6.3）
```

为什么拆四个而不是两个（原方案 `task.md` + `summary.md`）：

- 长任务里契约会被日志淹没，下一任读不到"当初到底要什么"
- 三个写者（planner 定契约、worker 记进展、loop 记状态）争一个文件，必然互相覆盖
- 拆开后**并发写问题在协议层消失**，不需要锁，只需要"别越界"

写权矩阵：

| 文件 | planner | worker | loop | 人 |
|---|---|---|---|---|
| `CLAUDE.md` / `OBJECTIVE.md` | 读 | 读 | 读 | **写** |
| `STATE.md` | **独占写** | 读 | 读 | 读（紧急可写，标 `[human]`） |
| `task.md` | 写一次 | 读 | 读 | 读 |
| `log.md` | **不读** | 追加 | 读尾部（只为拿断点提示） | 读 |
| `summary.md` | 读 | 写 | **只看在不在 + 有没有 `status:`** | 读 |
| `.state` | 读 | 不写 | **独占写** | 读 |
| `human.log` | 读（最新指令优先） | 读 | **独占写**（人通过 `-p` 说话，由 loop 落盘） | 读 |

## 三、会话模型与接力

| 会话 | 何时起 | session id | 记忆靠什么 |
|---|---|---|---|
| **planner** | 启动 / 任务关闭 / 队列空 / 停滞 | 每次新建 | `STATE.md` |
| **worker** | planner 指定了 `next_task` | 每任务固定一个，复用 | 会话本身 + `log.md` |
| **wrap-up** | 超时硬停 / worker 退出但无 summary | **优先复用原会话** | 会话本身（含全部中间结果）+ `task.md` |

两处不对称，都是刻意的：

- **planner 永远新会话**：否则它会长成第二个会膨胀的 worker，全局判断力下降。
- **wrap-up 优先复用原会话**：收尾是"提取"，不是"审判"。`log.md` 只记了结论性的几行，会话上下文里还留着原始输出、没写进日志的观察、差一点的半成品——**中间结果也是结果**。防自我辩护靠"summary 是证词，判的人是 planner"，不靠"剥夺它的上下文"。

### 3.1 两级接力

| 层级 | 触发 | 传递介质 |
|---|---|---|
| **任务间** | worker 写完 summary 退出 | `summary.md`（≤30 行）+ `task.md` → planner 定下一个 |
| **任务内** | 单任务超长、上下文将满 | worker 写 `## 断点` 到 `log.md` 后退出，同任务新会话续做 |

第二级最容易被忘，但长任务一定会撞上。任务内接力不改变状态机——只是换了个执行者。

### 3.2 `-r` 的真正用途

`claude -p` 是阻塞的，**没有向运行中进程注入消息的通道**。所以"提醒"只能 = 杀进程 + `--resume` 同一 session。这就是"每任务固定 session id"的真正理由：**不是为了省 token，是为了让提醒落进正确的上下文**。

```
首次：claude -p --session-id <uuid> "<worker bootstrap>"
提醒：claude -p --resume <uuid>     "<提醒 + 剩余预算>"
```

## 四、时间：时钟归驱动器

预算写在 `task.md` 的 `budget_min`（planner 定，默认 30）。阶梯按**剩余比例**定义，与分钟数解耦：

| 触发点 | 动作 | 提醒要点 |
|---|---|---|
| 剩余 50% | kill + 同会话续接 | 假设还成立吗？下一步是什么？ |
| 剩余 25% | kill + 同会话续接 | 收敛：先确保有可交付成果 |
| 剩余 5% | kill + 同会话续接 | 立即写 summary 并退出 |
| 归零 | kill + 同会话续接（收尾） | 停止推进，汇报实际进展，中间结果也算结果 |
| 收尾仍无 summary | 新会话只读文件兜底 | 机械降级路径，不常用 |

对应 30 分钟预算就是 15 / 22.5 / 28.5 分钟。想精确 15/10/5 就配绝对值，这是配置不是协议。

**代价要说清楚**：每次提醒都会丢掉在飞的工具调用（长跑爆破、编译会断）。对策是 `log.md` 的 `## 断点` 纪律 + 长操作必须可续。这条"可中断性"要求是协议逼出来的，不是洁癖。

## 五、中断与恢复：一张清单，一套机制

**不做运行中注入通道**（没有 INBOX，没有热插话）：人说话必须先让 loop 停下来（`-c -p` 也守这条，§5.4）。但中断有两种，都必须能接回来：

| 中断 | 怎么发生 | 人要做的事 |
|---|---|---|
| 人主动停 | Ctrl+C，为改目标 / 改优先级 | 改文件，然后 `-c` |
| 意外停 | 终端关、机器重启、OOM、SSH 断、loom 自己崩 | **什么都不用做**，`-c` |

两者共用一套机制，因为**从文件系统看它们没有区别**：loop 不在跑了，最后一个会话半途而废。

### 5.1 会话清单（照搬参考项目，别重新发明）

`work/sessions.log`，append-only：

```
2026-10-30T17:41:03  b3f1…  worker   task-03-parse-pcap  start
2026-10-30T17:56:03  b3f1…  worker   task-03-parse-pcap  remind1
2026-10-30T18:11:03  b3f1…  worker   task-03-parse-pcap  exit(143)
2026-10-30T18:11:09  b3f1…  wrapup   task-03-parse-pcap  start
2026-10-30T18:12:40  a77c…  planner  -                   exit(0)
```

三个细节直接沿用已验证的实现：**启动前就追加**（进程被硬杀时清单里也有它）、**从尾部向前扫第一个合法行**（容忍崩溃留下的残缺行）、**超过 200 行裁掉头部**。

`-c` 的动作：**取最后一条仍在进行的 sid 去 `--resume`**，不判断"上次是正常结束还是崩了"。

### 5.2 识别"假活"

`.state` 里除 sid 外记 `pid` 与**启动时刻**（`/proc/<pid>/stat` 第 22 字段）。`-c` 启动时：

- pid 不存在 → `running` 改成 `interrupted(pid gone)`
- pid 存在但启动时刻对不上 → pid 被复用，同样按中断处理

只记 pid 不够：pid 会被复用，只查"这个号还在不在"迟早把无关进程当成自己的会话。

还有一种更要紧的情况：**pid 活着，但 loop 已经死了**。那是上一任留下的孤儿，没人看着它，它却还在写文件。`-c` 的正确动作是**先杀掉再接**，否则会出现两个进程操作同一个 session。

### 5.3 恢复提示词：只说"被中断过"，不说怎么恢复

不区分人停还是意外停——模型判断不了，且第一件事本来就一样：

```
【中断恢复】本会话之前被中断过（可能是人按了 Ctrl+C，也可能进程/机器意外退出）。
先核对现状（环境是否还在、文件是否被人改过），再谈续接；不要假设中断前的东西还成立。
核对顺序：git status → git log -1 → log.md 尾部。前两个是机器写的，先信它们。

【人的指令】（仅在 -c 带了 -p 时出现；没有这段就跳过）
<人的原话>
这是人刚刚说的话，优先级高于文件里的旧计划。但它不能替代 OBJECTIVE.md 的验收标准：
若它与目标冲突，照做，但不要宣布达成，并在 STATE.md 记一行 [needs-human] 指令与目标冲突。
若你当前任务与它冲突：停手，写 summary.md（status: failed，原因"人已改变方向"）再退出。
```

**"怎么核对"不写步骤。** 环境要不要重建、断点命令要不要重跑、要不要从头定位，取决于任务在做什么。写成"查进程 → 读三个文件 → 跑断点命令"，只会让简单场景做无用功、复杂场景漏掉真正该查的。一句"先核对再接续"，模型自己会去找该核对什么。

唯一写死的是那条**冲突规则**——因为它是权限问题，不是判断问题：worker 无权决定"旧任务还值不值得做完"。

### 5.4 人怎么说话：`-c -p "..."`

人介入除了改文件，还可以直接说一句。它不新建通道，只是给"停 → 改 → 续"这条路加了个更省事的入口：

```
loom.py -c -p "这题别打了，转去打 web-02"
loom.py -c -p "flag 格式是 flag{...}，别猜别的" -p "这题只给 20 分钟"
```

`-p` 在不同上下文里是**两件事**，必须在命令行上分清楚：

| 调用 | 含义 |
|---|---|
| `loom.py -p "目标"`（工作区里还没有 `OBJECTIVE.md`） | **建立目标**，落盘成 OBJECTIVE |
| `loom.py -p "..."`（`OBJECTIVE.md` 已存在） | **人介入**：记进 `human.log` 并注入被续接的会话；loom 打印一行"改目标请直接编辑 OBJECTIVE.md" |
| `loom.py -c -p "..."` ×N | 多条按顺序拼成一段注入 |

**为什么必须落盘到 `human.log`，而不是只塞进这一次 resume 的 prompt：**

只注入一次，这任会话死了，下一个 worker 从没听过这句话。人会以为"我说过了"，而这正是当初拒掉 INBOX 时要防的那个失败面。落盘 + planner 每轮读，"同步说的话"就变成了"持久的事实"，代价只有一行 append。

`human.log` 只有两种条目，都由 loop 写：

```
2026-10-30T17:59  [via -p]    这题别打了，转去打 web-02
2026-10-30T18:20  [via 文件]  OBJECTIVE.md 被改（mtime 变化）
```

第二条是机械检测（`-c` 启动时比 mtime / hash）。它让"人到底改过什么"有记录，事后不必靠回忆。

`human.log` 也吃预算：超过 60 行时 loop 把最旧的移进 `human.archive.log`，活文件只留最近 60 行。理由和 `sessions.log` 裁头一样——**planner 每轮都要读它**，一个无限增长的人话文件迟早把全局判断挤掉。

**一条权限边界（必须写死）**：`-p` 的话优先级很高，但**不能改验收标准**。目标要变只能改 `OBJECTIVE.md`。若口头指令与 OBJECTIVE 冲突，正确动作是：照做，但不宣布达成，并在 `STATE.md` 记一行 `[needs-human] 指令与目标冲突`。这不是不信任人，是保住"执行方不能自己定义成功"这唯一一道闸门（§八 第 4 条）。

> 这仍然**不是**运行中注入通道：人必须先 Ctrl+C 让 loop 停下来。**能说话的前提是已经停了**——保留这个约束，才没有"人以为说过了、模型没看见"的窗口。

## 六、版本管理：git 是记忆的第四层

**文件即记忆**这条基调只说了一半。文件能不能被**还原**、被**对比**、被**退回去**，是另一半。git 免费提供这三件事，代价只有一条纪律。

三个能力，正好对上三个失效模式：

| git 给的 | 治什么 | 怎么用 |
|---|---|---|
| `git log` | 交接幻觉：上一任说"做完了"，其实半成品 | **commit 摘要比 summary.md 硬**——summary 是自述，commit 是动作记录 |
| `git diff` / `git status` | 假完成：声称改了，其实没落地 | 恢复时第一眼看它，比读任何文档都快 |
| `git reset` / `revert` | 沉没成本：方向错了还在往下挖 | **"放弃一条路"终于有了执行手段**，不再只是写一句"别再试" |

> 最后一条是质变。没有 git 时，"放弃"等于"记住不要再来"，靠人自觉；有 git 时，放弃 = 回到分叉点，把试过的写进 `shared/deadends/`，然后从干净状态重新开始。**这是唯一一个能让 agent 敢于大胆试错的机制**——因为它知道退得回去。

### 6.1 谁在什么时候提交

**不给 loop 做常规提交。** 提交由模型做，理由和"验收不写进流程"一样：什么时候提交、提交什么粒度，是判断。写死成"每 N 分钟提交一次"只会产生一堆 `auto commit` 噪音。

| 谁 | 何时 | 提交信息 |
|---|---|---|
| worker | 每完成一个**可验证**的小步 | `[task-NN][feat] 增量爆破出前 3 字节，脚本 solve/brute.py` |
| worker | 会话退出前，**写完 summary 之后** | `[task-NN][docs] summary: partial，卡在 XX` |
| planner | 每次重写 `STATE.md` 之后 | `[plan] 关闭 task-03，新开 task-04 走 XX 路线` |
| loop | **只在异常退出且工作区脏时**，兜底一次 | `[checkpoint] worker task-03 异常退出 (sid b3f1)` |

最后一行是流程分支，归 loop：会话结束 → `git status --porcelain` 非空 → 说明有人没提交就走了 → 兜底打一个 checkpoint。**正常路径不要它，异常路径靠它不丢东西。**

### 6.2 三条硬规则

1. **只 `git add` 自己写的路径，绝不用 `git add -A` / `git commit -a`。**
   单一写者在 git 里的等价物。串行时影响小，但人一介入（改了 `OBJECTIVE.md` 又没提交），worker 的 `-A` 会把人家的修改顺手塞进自己的 commit 里——事后完全看不出是谁改的。

2. **禁止 `git checkout .` / `git reset --hard` / `git clean -fd`。**
   这三个会不可逆地吞掉"别人写过但没提交"的东西。要回退就退到**明确的 commit sha**，并且只允许退自己这条线上、`git status` 干净的时刻。

3. **单线，不建分支。**
   分支会让"文件即记忆"失效——下一任打开工作区，不知道自己站在哪条时间线上。串行 + 单线是所有接力设计里最省心的组合。

### 6.3 `.gitignore` 的分界线：什么进 git，什么不进

分界不是"大小"，是**能不能重建**：

```gitignore
# 必进：契约 / 结论 / 状态 / 脚本 / 清单
#   CLAUDE.md  OBJECTIVE.md  STATE.md  tasks/**/*.md  shared/  sessions.log

# 不进：可重建的中间物
tasks/*/artifacts/          # 解包、反编译、dump、下载的镜像
**/node_modules/  **/__pycache__/  *.log  *.tmp
.venv/  dist/  build/
```

判据一句话：**只留 `task.md` + `log.md` + `summary.md` + `solve/`，能不能重放整条路径？** 能，说明成果没留在会丢的地方；不能，说明该进 git 的东西还躺在 `artifacts/` 里。

> 例外要写清：**一击致命的小证据必须进 git**——flag 的原文、关键那段 hexdump、对方服务的 banner。它们小到不值得省，丢一次却要重来两小时。

### 6.4 恢复时先看 git（这条比读文档快）

`-c` 之后，最可靠的三条事实按顺序是：`git status`（有没有没提交的东西）→ `git log -1`（上一任最后干了什么）→ `log.md` 尾部（上一任以为自己在干什么）。

前两条是机器写的，第三条是人写的。**先看机器写的。**

顺带一个真会撞上的坑：git 被硬杀时会留下 `.git/index.lock`。恢复时若它存在且没有 git 进程在跑，删掉它——否则后面所有提交都会失败，而错误信息看起来像"仓库坏了"。

> **一个必须提前说清的边界：git 不是机械化验收的回归。**
> 不要写"loop 检查最近 N 分钟有没有 commit"这类规则——那正是 §7 刚扔掉的东西换了个马甲。
> git 的价值在**下一任能看懂、能退回**，不在**这一任被检查**。谁违背了这条，框架会迅速退化成"提交 KPI"，然后模型开始为提交而提交。

## 七、验收：把 summary 当证词

**框架不做质量验收。** 只在 planner 的 prompt 里写明立场：

> `summary.md` 是上一个 worker 的**自述**，不是经过核实的结论。你可能信、可能存疑、可能觉得需要复核；依据它的可信度决定继续推进还是先开一个复核任务。这个判断不必每次都用同样力气。

三条理由：

1. **注意力是稀缺资源。** 验收做到什么程度本身就是判断，写成流程等于取消这个判断，还占掉 planner 想"下一步做什么"的注意力。
2. **机械校验只挡低级造假。** 路径存在但结论错、命令跑通但前提错，脚本永远查不出来。
3. **现实里通常已经有裁判。** 赛题有分数、代码有测试、数据有指标——真伪不需要框架再判一遍。框架只需要保证**陈述和执行是两个人**。

loop 唯一保留的检查是**流程分支**，不是质量判断：`summary.md` 在不在、有没有 `status:` 这一行。内容一个字都不读。

> 分界线一句话：**机器只数文件，模型才读内容。**

## 八、不变量（9 条，全部价值在这）

1. **文件即记忆**：会话退出前必须留下"下一步"，哪怕是 failed。
2. **单一写者**：每个文件只有一类角色可写。
3. **契约冻结**：`task.md` 创建后不可改，要改就新建任务。
4. **目标不可协商**：`OBJECTIVE.md` 只有人能改，planner 不得放宽验收标准；人的口头指令（`-c -p`）同样不能改它（§5.4）。
5. **planner 不干活，worker 不改计划。**
6. **过程层永不进 planner 上下文**（`log.md`、产物、原始素材）。
7. **机器判事实，模型判语义**：时钟、退出码、文件存在性、`git status` 归 loop；成没成归 planner。
8. **序号单调递增，名字永不复用。**
9. **可回退**：每个会话边界都留下一个可用的 commit，任何一任都能退回上一个可用状态（§6.1）。

### 8.1 机械违例检测（可选，默认关）

只做一件零成本、零注意力的事：**会话前后对关键文件做 mtime 快照**。变了就记 `violation: worker_wrote_state` / `violation: planner_wrote_task_files` 到 `sessions.log`。

它是**观测**，不是拦截——发现了只记录，让 planner 下一轮看到。默认关闭，干跑阶段打开用来确认协议真的被遵守。

| 扔掉 | 原因 |

6 条干跑场景全部通过：正常闭环 / 不写 summary / 崩溃 137 / 时钟阶梯 / planner 空转 / `kill -9` 后 `-c` 接回。

### P0 · 骨架（半天）

产出：`work/` 模板 + 宪法。

### P1 · `loom.py` 串行闭环（1 天）

单文件，约 350 行。只做流程：

```
loom.py -p "目标"                  # 建骨架 → planner bootstrap → 主循环
loom.py -c                         # 从 sessions.log 接回，注入 recovery
loom.py -c -p "…" [-p "…"]         # 接回 + 注入人的话（写 human.log，§5.4）
loom.py --status                   # 打印队列与 .state（可选）
```

内部就六件事：**spawn 会话 / 记 sessions.log / 跑时钟阶梯 / 写 .state / 判定"有没有 summary" / 异常退出时打 git checkpoint**。不解析任何自然语言。

git 相关只有两处，都是机械判断：

- 会话开始前：`.git/index.lock` 存在且无 git 进程 → 删掉（否则后面所有提交都会失败，报错还像"仓库坏了"）
- 会话结束且非正常退出：`git status --porcelain` 非空 → `git add`（仅该会话碰过的路径）+ 一次 `[checkpoint] <role> <task> 异常退出 (sid …)`

完成判据：拿一个假目标（"写一个 hello world 到 out.txt"）跑通 bootstrap → worker → 关闭 → planner → `PROJECT: DONE` 全链路，全程无人工干预。

### P2 · 恢复路径（半天）

- `-c`：读清单 → 校验 pid/pid_start → resume 并注入 recovery 提示
- **resume 后按角色分流**（易漏）：恢复的是 worker 会话 → 走同一套"收尾判定 → planner"路径，**不能重新 spawn 一个新会话**（同 session id 二次 `--session-id` 会失败，且会造成重复执行）
- Ctrl+C：给子进程 5 秒优雅退出（转录落盘才能被 `-r` 接回），超时才 terminate，然后打印"已停止，改完文件用 `-c` 续跑"
- 恢复提示词点明信息源顺序：`git status` → `git log -1` → `log.md` 尾部（机器写的先看，§6.4）
- `-p` 的两种含义按"`OBJECTIVE.md` 存在与否"分流；已有目标时打印一行提示，再写 `human.log`
- `-c` 启动时比对 `OBJECTIVE.md` / `STATE.md` / `task.md` 的 mtime（存 `.loophash`），变了就写一条 `[via 文件]` 到 `human.log`——**这是记录，不是拦截**

### P3 · 干跑：8 个必测 + 3 个观察（1 天）

**验收目标不是"能不能把事做成"，是"接力断不断"。**

| # | 注入 | 期望 |
|---|---|---|
| 1 | worker 中途 `kill -9` | 下一任从 `log.md` 断点续上，`.state` 记 `exited` |
| 2 | worker 不写 `summary.md` 就退出 | 收尾会话**复用原会话**被拉起，把中间结果写进 summary |
| 3 | 预算设 3 分钟，让 worker 死循环 | 三个提醒依次触发；硬停后收尾产出 summary；项目继续 |
| 4 | Ctrl+C → 改 `OBJECTIVE.md` → `-c` | resume 回原会话；发现冲突 → 停手写 `status: failed` → planner 重排 |
| 5 | `kill -9` loom 自己 → `-c` | 从清单接回；stale pid 识别为 `interrupted`；**无人参与也能接回** |
| 6 | 抹掉 session id 再触发超时 | 降级到只读文件的新会话，summary 仍产出 |
| 7 | 让 worker 走错方向，planner 决定回退 | planner 建「回退到 `<sha>` 并改走 Y」任务；worker 用明确 sha 回退，试过的路径落进 `shared/deadends/` |
| 8 | `-c -p "别打了，转去另一件事"` | 话落进 `human.log` 且拼进 resume；当前 worker 停手写 `failed`；**下一任 planner 仍能从 human.log 看到这句话** |
| 观察 A | worker 写"已完成"但产物不存在 | planner 是否把它当证词、是否开复核——**看行为是否合理，不要求拦截** |
| 观察 B | worker 去改 `STATE.md` | 违例检测是否记录（打开 §8.1 时） |
| 观察 C | worker 从不提交、直接退出 | loop 的 checkpoint 是否补上；`git log` 是否仍连续 |

跑通 8 条，骨架成立。之后才是调参和 profile。

### P4 · CTF profile（半天，赛前）

框架之上只加领域层，全部写进 CTF 版 `work/CLAUDE.md`：

- flag 提交纪律（从哪里提交、提交前后记什么、不猜 flag）
- 题目目录语义（`challenges/<cat>-<id>` 与 task 的对应）
- 领域红线和注入防护
- 多机使用约定（哪台机跑什么、共享目录怎么同步）
- 仓库边界：题目附件与解包产物进 `artifacts/`（gitignored），只把 `solve/` 与关键证据提交
- 裁判形态：提交结果由人/planner 看，框架不强制脚本化

### P5 · 调参（跑过真实任务后）

预算默认值、提醒点、是否开并行、`STATE.md` 的行数上限。**全部来自 P3/P4 的实测数据，不拍脑袋。**

### 写代码时才发现的四件事（都已进实现）

1. **`sessions.log` 必须存完整 sid。** 为了好看截成 `b3f1…`，`-c` 就拿不到能 resume 的 id——一个显示格式问题会让整套恢复机制失效。
2. **孤儿进程要先杀再接。** 只判断"pid 还在不在"会漏掉"pid 在，但 loop 死了"：那个子进程没人管，却还在写文件；再 resume 就是两个进程写一个会话。
3. **planner 需要空转守卫。** 队列空时它会一轮一轮地"再想想"，每轮都是真金白银。判据纯机械：连续 3 轮 `STATE.md` 字节未变 → 停机等人。这不是质量判断，是防失控。
4. **git 身份缺失会让所有提交静默失败。** 机器上没配 `user.email` 时，`git commit` 报错但没人看 stdout。`git init` 时顺手补一个 repo-local 身份，问题就没了。

## 十一、刻意不做（每一条都是主动放弃，不是没想过）

1. **不做并行**：单 worker 串行。`.state` 已按任务隔离，扩展位留着，但调度与一致性等串行跑稳再说。
2. **不做机械化验收**：见 §7。
3. **不做成本记账**：只有墙钟，没有 token 预算。
4. **不做跨项目记忆**：`shared/` 只在项目内。
5. **不做多 agent 对话**：两个角色之间只有文件，没有对话。**沟通成本为零，这是设计目标，不是妥协。**
6. **不做运行中注入通道**：见 §5。`-c -p` 不算通道——它要求人先把 loop 停下来。
7. **不做分支、不做自动 merge、不做自动 push**：单线单机。git 在这里是"存档 + 回退"，不是协作工具。想要跨机共享再把 remote 加上（见 §12 第 4 条）。

## 十二、still open（实现中验证，不阻塞开工）

1. **planner 空转**：队列空时它可能反复"再想想"。目前只给一句"别为了填队列造无意义任务，没价值就宣布结束"，不设硬阈值。P3 观察实际行为再决定要不要加。
2. **任务内接力的触发时机**：现在让 worker 自评"上下文过半"写断点。这个自评准不准，P4 拿真题才知道。
3. **`STATE.md` 的膨胀**：55 个任务时它会不会涨到 300 行。届时可能要把"任务表"拆成独立文件，让 `STATE.md` 只留队列与判断。
4. **多机怎么同步**：CTF 有 4 台机。最小方案是其中一台做 bare remote，其余 `pull --rebase` 后 `push`；但 rebase 与"单一写者"会打架。串行 + 一机一题下可以先不碰，等真的要并行再解。

## 附录 A · 四个 prompt（能跑起来的最小集）

**planner bootstrap**
```
你在 work/ 下工作。读 CLAUDE.md、OBJECTIVE.md。
把目标拆成可独立完成、可独立验收的任务。
输出：重写 STATE.md（任务表 + next_task + 全局判断），并创建第一个任务的 task.md。
本次会话不做任何实质工作——只做规划。改完后提交：[plan] 初始拆分。
```

**planner 轮次**
```
读 STATE.md、OBJECTIVE.md、human.log（人说过的话全在那，越新越优先），以及各任务的 task.md 与 summary.md。
不要读 log.md 或产物。
summary.md 是上一个 worker 的自述，不是核实过的结论——信多少由你判断，
需要核实就开一个复核任务，不必每次都核。
输出：更新 STATE.md（关闭任务、重排队列、写 next_task 与决策日志一行），然后提交：[plan] …。
若目标已达成或已不可达，写 PROJECT: DONE / BLOCKED 并给出逐条依据。
如果你判断某个方向已经错了，可以新建一个「回退到 <sha> 并改走 Y」的任务，而不是让 worker 在原地继续。
```

**worker**
```
你要完成的是 tasks/<task-id>/。
顺序：读 CLAUDE.md → 读 task.md → 读 log.md 尾部 → 若 log.md 有「下一步命令」先验它。
每个有意义的步骤追加 log.md（一条 ≤5 行）；上下文过半时写 ## 断点 再退出。
每完成一个可验证的小步就提交一次：[task-NN][feat] 做了什么 + 怎么验证的。
只 git add 你自己写的路径（绝不用 -A）；不建分支；不 reset --hard、不 checkout .、不 clean -fd。
结束前必须写 summary.md（status + 结论 + 产出在哪 + 下一步），并提交一次。
你只能写本任务目录内的文件，不得修改 STATE.md，不得创建新任务。
```

**收尾（复用原会话）**
```
【超时收尾】本轮已超预算，停止推进，只做汇报。
把实际拿到的结果写进 tasks/<task-id>/summary.md：做了哪些尝试、哪些有产出、
哪些半成品还差什么、卡在哪、下一步该谁做什么。
中间结果也是结果：跑出来的数据、验证过的结论、排除掉的路径，都写清楚。
status 用 done / partial / failed。写完即退出，不要继续推进，不要改动其他文件。
```
